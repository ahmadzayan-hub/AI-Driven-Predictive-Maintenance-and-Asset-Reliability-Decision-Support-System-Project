## Environment gotchas

Browser tests select `PYTHON_EXECUTABLE`, then the project venv, then `python3`. The locked-SQLite cleanup errors are fixed (`a036cf9`, then `3f27e0a` for stages, tenancy and the backup drill) and no CRLF fixture mismatch appeared; if errors return, suspect a new test that leaves a store open inside a `TemporaryDirectory` and reach for `closing`/`closing_store` in `tests/support.py`. Two load-dependent flakes remain and are not code faults: a child interpreter can die with `_Py_HashRandomization_Init` under full-suite load, and `vitest` can fail to spawn workers ("Timeout waiting for worker to respond") on a busy machine - re-run the frontend suite alone before believing it. **Adding a frontend test file does the same thing at a smaller scale (20 Oct):** as a 34th file, 12 new tests made 5, 19 and 14 *unrelated* tests fail across three runs, every one a `findBy` query at its 5 s timeout, against 232 of 232 green on two baselines without it. Both register `addCleanup`, which runs at **teardown** - so a test whose temporary directory is a `with` block *inside* the test body needs `contextlib.closing` around the store instead, because the directory goes first. A shared helper takes `case=None` as a trailing keyword, never a new first positional: `engine_in` is imported across test files and a positional change breaks callers you did not grep for. This was 93 of the suite's errors on 19 October; it is a defect, not noise.
