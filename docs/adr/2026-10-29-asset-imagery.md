# Asset imagery on asset cards: options for the owner's decision

Date: 2026-10-29 · Status: **Proposed, awaiting the owner's decision.** No code
is written for it. This record exists because the feature cannot be built as
an interface change alone.

## Context

The interface list in `project-progress.md` asks for imagery-led asset cards.
Today an operation asset is a row in `operation_assets` (`external_id`,
`source_system`, `name`, `criticality`, `site_id`). There is no image field,
no upload path for images, and no storage for them. The assets view therefore
has nothing to show but text.

Adding imagery means three decisions the code cannot make:

1. **Source.** Where do the pictures come from? The organisation's own photos,
   a source system that supplies an image URL, or pictures generated by a model.
2. **Privacy.** Photographs of equipment can show people, site plans, badges,
   or identifiers. The project's rules forbid raw data reaching a model and
   require that uploads are treated as data, never as instructions.
3. **Storage and limits.** Images stored in the database count against the
   tenant's data, and their size affects page weight and the hosted plan.

## Options

**A. Organisation uploads a photo per asset (recommended).**
A managing user attaches one photo to an asset. The server accepts only PNG or
JPEG, up to 300 KB, strips metadata (EXIF, GPS), re-encodes the image, and
stores it in the database with the asset. The asset card shows it with
alternative text that the user must write, in English and Arabic.
- For: no model involved; the owner controls every picture; the same
  authorisation as the asset.
- Against: a new upload endpoint, a new table column or table, and a
  re-encoding dependency to review.

**B. The source system supplies an image URL.**
A connector field carries a URL; the server fetches and caches the image.
- For: no manual work once a connector exists.
- Against: fetching remote content is a new outbound surface, and the source
  system's image rights and privacy are outside this project's control.

**C. Generated illustrations by an image model.**
- Against: a picture of a machine that does not exist misleads a reader. The
  project's rules rule this out for evidence. Not recommended.

**D. Keep text cards; add a colour and criticality marker only.**
- For: nothing to store and nothing to review.
- Against: does not meet the request for imagery.

## Recommendation

Option A, limited to PNG and JPEG, 300 KB, metadata removed, alternative text
required, and the card falls back to the current text card when no photo is
attached. Option B only after A exists and a source system asks for it.

## What the owner must decide

1. Option A, B, C or D. If A, confirm the size limit and formats.
2. Who may upload a photo: managers only, or every operator with write access.
3. Whether a photo may show people. If the answer is "not allowed", the upload
   needs a check that is not automated here, and the owner must say who does it.
4. Whether the hosted database may hold the photos, given its plan limits.

Nothing in this record changes the application. Once the owner chooses, the
work becomes an ADR of its own with tests in the same slice, as the programme
requires.
